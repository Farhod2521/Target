# A. YANGI FUNKSIYALAR

## 1. Ofis v2: Sotuv va Support kanbanlari

### 1.1. Jarayon

Ofisdagi Sotuv bo'limining yangi versiyasi ikkita alohida kanbandan iborat:

- **Sotuv** (`sales`). Ro'yxatdan o'tib to'lamaganlar lead bo'ladi. Menejerlar ularni
  oladi, bog'lanadi, natijani belgilaydi. Mijoz to'lasa, karta o'zi «Sotildi»ga o'tadi.
- **Support** (`support`). To'lagan mijozga yordam kerak bo'lgan har holatda (sozlash
  tugamagan, Meta xatosi, so'rovnomada yordam so'radi, reklama ishlamayapti) mijozning
  **bitta** kartasi ochiladi. Yangi sabablar shu kartaga qo'shiladi.

Hamma yo'llar `/api/v2/office/...` da. v1 (`/api/v1/office/sales/...`) o'zgarmagan va
v2 ga aralashmaydi.

Hamma so'rovlar xodim tokeni bilan yuboriladi: `Authorization: Bearer <token>`.
Ruxsati yo'q xodimga yoki mijozga hamma yo'l **404** qaytaradi.

Kanbanni har **30 soniyada** qayta so'rab turing. WebSocket yo'q.

Migratsiya **0038**: `board_settings`, `board_columns`, `board_cards`,
`board_card_events`, `survey_help_options`.

### 1.2. Kim nimani ko'radi

| Rol | Ko'radi | Qila oladi |
|---|---|---|
| `Sales` (Sotuv menejeri) | Sotuv kanbani, faqat o'z kartalari | Lid olish, tugmalar, izoh |
| `SalesLead` (Sotuv rahbari) | Butun Sotuv kanbani, «Ishlanmagan» va «Yopildi» ham | Kartani menejerga berish yoki qaytarib olish |
| `Support` | Butun Support kanbani | Tugmalar, izoh |
| Superuser va `Owner` | Ikkala kanban | Hammasi: ko'chirish, ustunlar, xodimlar, so'rovnoma belgilari |

#### `GET /api/v2/office/me`

Sahifa ochilganda birinchi shu chaqiriladi.

```json
{
  "user": {"id": "…", "name": "Ali", "email": "ali@…"},
  "roles": [{"value": "Sales", "label": "Sotuv menejeri"}],
  "is_superuser": false,
  "boards": [{"code": "sales", "label": "Sotuv", "lead": false}],
  "default_board": "sales",
  "can": {"take": true, "assign": false, "move": false, "columns": false, "staff": false}
}
```

- `boards` bo'sh bo'lsa, bu xodimga kanban yo'q: menyuda ko'rsatmang.
- `default_board`: birinchi ochiladigan kanban.
- `can.take`: «Lid olish» tugmasi.
- `can.assign`: kartani boshqa xodimga berish.
- `can.move`, `can.columns`, `can.staff`: faqat superuser va Egasi uchun.

### 1.3. Kanban

#### `GET /api/v2/office/boards/{board}`

`board`: `sales` yoki `support`. Parametrlar (hammasi ixtiyoriy):

| Parametr | Ma'nosi |
|---|---|
| `q` | Mijozning ismi, emaili yoki telefoni bo'yicha qidiruv |
| `column` | Faqat bitta ustun (keyingi sahifa uchun) |
| `offset`, `limit` | Shu ustunning sahifasi; `limit` 1–200, odatda 50 |

```json
{
  "board": "sales",
  "columns": [
    {
      "code": "new_lead", "name": "Yangi lead", "position": 2,
      "kind": "manual", "is_final": false, "total": 12,
      "cards": [
        {
          "id": "…", "board": "sales", "column": "new_lead",
          "client": {"id": "…", "name": "Vali", "email": "…", "phone": "+998…", "signed_up_at": "…"},
          "manager": {"id": "…", "name": "Ali", "email": "…"},
          "contact_mark": "", "needs_support": false, "reasons": [],
          "opened_at": "…", "column_since": "…", "closed_at": null
        }
      ]
    }
  ]
}
```

- Ustunlar `position` tartibida keladi. Ofis ularning nomini va tartibini
  o'zgartirishi mumkin, shuning uchun mantiqni hech qachon nomga emas, **`code`** ga
  bog'lang.
- `total`: ustundagi kartalar soni (qidiruv hisobga olinadi). Kartalar dastlab 50
  tadan keladi, qolganini `?column=<code>&offset=50` bilan oling.
- Kartani sudrab ko'chirib bo'lmaydi (drag-and-drop yo'q). Karta faqat tugma yoki
  avtomatik hodisa bilan ko'chadi.

#### `GET /api/v2/office/boards/{board}/columns`

Faqat ustunlar (kartasiz) va `live_since`, ya'ni kanban ishga tushgan vaqt.

#### Ustunlar

**Sotuv:**

| `code` | Nomi | Turi | Kim ko'radi |
|---|---|---|---|
| `unworked` | Ishlanmagan | avto | Rahbar |
| `new_lead` | Yangi lead | tugma | Ega menejer, rahbar |
| `no_contact` | Bog'lanilmadi | tugma | Ega menejer, rahbar |
| `contacted` | Bog'lanildi | tugma | Ega menejer, rahbar |
| `sold` | Sotildi | avto, yakuniy | Ega menejer, rahbar |
| `closed` | Yopildi | tugma, yakuniy | Rahbar |

`trial`, `discount_20`, `discount_10`, `no_discount` ustunlari bazada bor, lekin hozircha
yashirin va javobda kelmaydi. Bepul sinov va chegirma qilinganda paydo bo'ladi.

**Support:** `new` (Yangi), `in_progress` (Ishlanmoqda), `resolved` (Hal qilindi, yakuniy).

### 1.4. Karta

#### `GET /api/v2/office/cards/{id}`

Javobda kartaning hamma maydonlari, hamda:

```json
{
  "client": {"…": "…", "role": "business", "language": "uz", "last_login": "…",
             "plan": {"name": "Standart", "status": "active", "expires_at": "…", "setup_done": false}},
  "ticket_reasons": [{"code": "meta_error", "label": "Meta xatosi", "detail": "Reklama ishga tushmadi: …", "at": "…"}],
  "support_chat_id": "…",
  "close_reason": "expensive", "close_reason_label": "Qimmat", "close_note": "",
  "actions": [{"value": "contacted", "label": "Bog'lanildi"}],
  "history": [{"kind": "taken", "label": "Lid olindi", "from_column": "unworked", "to_column": "new_lead",
               "actor": {"id": "…", "name": "Ali", "email": "…"}, "body": "", "at": "…"}]
}
```

- **`actions`**: kartada ko'rsatiladigan tugmalar, tartibi bilan. Faqat shularni chizing.
- `history`: eng yangisi birinchi. `actor: null` bo'lsa, buni tizim qilgan.
- `ticket_reasons`: Support kartasi nega ochilgani, eng yangisi birinchi.
- `support_chat_id`: mijozning Yordam chati bo'lsa, shu chatni ochish uchun.

#### `POST /api/v2/office/sales/take`

«Lid olish». Body yo'q.
- Eng eski «Ishlanmagan» lid shu menejerga beriladi va «Yangi lead»ga o'tadi.
- Javob: karta (yuqoridagi shakl).
- Lid qolmagan bo'lsa: **409** `nothing_to_take`.
- Faqat Sotuv rollarida ishlaydi.

#### `POST /api/v2/office/cards/{id}/actions`

```json
{"action": "contacted", "note": "Ertaga to'laydi"}
```

| `action` | Qaysi ustunda | Nima bo'ladi |
|---|---|---|
| `contacted` | Yangi lead, Bog'lanilmadi | → Bog'lanildi |
| `no_contact` | Yangi lead | → Bog'lanilmadi |
| `needs_support` | Bog'lanildi | «Support kerak» belgisi; `"on": false` olib tashlaydi |
| `close` | Yangi lead, Bog'lanilmadi, Bog'lanildi | → Yopildi; `reason` majburiy |
| `start` | Support: Yangi | → Ishlanmoqda; bosgan xodim mijozning doimiy mas'uli bo'ladi |
| `resolve` | Support: Ishlanmoqda | → Hal qilindi |

- `close` uchun `reason` qiymatlari `GET /api/v2/office/boards/sales/reasons` da:
  `expensive`, `not_needed`, `no_answer`, `wrong_number`, `other`.
  `other` bo'lsa, `note` majburiy.
- Boshqa hollarda `note` ixtiyoriy va tarixga yoziladi.
- Javob: yangilangan karta.

#### `POST /api/v2/office/cards/{id}/notes`

```json
{"body": "Qayta qo'ng'iroq qilish kerak"}
```

#### `POST /api/v2/office/cards/{id}/assign`

Kartani xodimga beradi. Sotuvda buni rahbar qiladi, Support'da superuser yoki Egasi.

```json
{"staff_id": "…"}
```

- `"staff_id": null`: kartani qaytarib olish. Sotuv kartasi «Ishlanmagan»ga, Support
  kartasi «Yangi»ga qaytadi.
- Kimga berish mumkinligi: `GET /api/v2/office/boards/{board}/staff`.

#### `POST /api/v2/office/cards/{id}/move`

Superuser va Egasi uchun: kartani shu kanbanning istalgan ko'rinadigan ustuniga ko'chirish.

```json
{"column": "closed", "reason": "Dublikat"}
```

- `reason` majburiy.
- Yakuniy ustunga ko'chirilsa karta yopiladi, undan chiqarilsa ochiladi.
- «Ishlanmagan»ga ko'chirilsa, kartadan menejer olinadi.
- «Sotildi»dan qo'lda chiqarilgan karta Egasi qo'ygan joyda qoladi: avtomatik
  «Sotildi» qoidasi uni qayta tortmaydi (9-bo'lim, №1).

### 1.5. Kartalar o'zi qachon paydo bo'ladi

Bu qoidalar faqat **deploydan keyin** bo'lgan hodisalarga ishlaydi. Kanban birinchi
ishga tushgan vaqt `live_since` da saqlanadi, undan oldingi hodisalar kanbanga tushmaydi.

**Sotuv** (har daqiqada):
- Ro'yxatdan o'tgan va hech qachon to'lamagan (to'langan yoki qaytarilgan hisob-faktura
  yo'q, faol obuna yo'q) → «Ishlanmagan»da lid.
  Xodimlar, superuserlar, CRM loginlari va bloklanganlar lid bo'lmaydi.
- Mijoz tarif uchun to'ladi → karta istalgan ustundan, «Yopildi»dan ham, «Sotildi»ga
  o'tadi. Bu har kartada **bir marta** bo'ladi.

**Support**: bitta mijozga **bitta** karta. Yangi sabab shu kartaga qo'shiladi, bir xil
sabab ikki marta yozilmaydi. «Hal qilindi»dagi kartaga yangi sabab kelsa, karta qayta
ochiladi va o'sha mas'ul xodimga qaytadi.

| `reasons` kodi | Qachon | Qanchada tekshiriladi |
|---|---|---|
| `setup` | Tarif uchun to'lovdan 1 soat o'tdi, sozlash tugamagan. Har to'lovga bir marta: uzaytirishda ham sozlash tugamagan bo'lsa, yana yoziladi | har daqiqa |
| `from_sales` | Sotuvda «Support kerak» belgisi qo'yilgan mijoz to'ladi (darhol, 1 soat kutilmaydi) | har daqiqa |
| `meta_error` | Reklamani ishga tushirish Meta xatosi bilan tugadi yoki rollback qilindi, yoki mijozning amali (yoqish/o'chirish va h.k.) Meta tomonidan rad etildi. Tizimning o'z qayta urinishlari va Meta'niki bo'lmagan rad etishlar (masalan, «allaqachon to'xtatilgan») kirmaydi | har daqiqa |
| `survey` | So'rovnomada ofis «yordam kerak» deb belgilagan variantni tanladi (oxirgi 24 soat) | har daqiqa |
| `idle` | To'lovdan 3 kun o'tdi, tarif hali faol, birorta reklama yoqilmagan | soatiga bir (har soatning 15-daqiqasida) |
| `idle` | Bizda yaratilgan kampaniya 24 soatdan beri yoqilgan, oxirgi 6 soatdagi o'qishda hali yoqilgan, lekin yoqilganidan beri sarf 0 (oxirgi 30 kun) | soatiga bir |

## 2. AI chat → Support: javob topilmasa mutaxassisga o'tkazish

### 2.1. Jarayon

AI yordamchi (`/chat`) ba'zi savollarga aniq javob topa olmaydi: to'lov, bloklangan
akkaunt, xato, mahsulot haqida javobi yo'q savol yoki mijoz «operator kerak» desa.
Shunda savol **avtomatik** Support'ga o'tadi. Frontend faqat natijani ko'rsatadi.

1. Model javob oxiriga `%%SUPPORT%%` belgisini qo'yadi. Bu prompt `chat_answer` v28 da
   kelgan. Belgi javob matnidan olib tashlanadi, mijoz uni ko'rmaydi.
2. **Login qilgan mijoz.** Savol uning support chatiga **o'z nomidan** yoziladi
   (`source: "ai_chat"`). Matni:
   ```
   🤖 AI yordamchi bu savolga javob topa olmadi.

   Savol: <savol>

   AI javobi: <AI javobi, ko'pi bilan 600 belgi>
   ```
   Support xodimlariga Telegram staff botda «· AI chatdan» belgisi bilan boradi.
   Bir mijozdan soatiga ko'pi bilan 3 ta. Bir xabar ikki marta yuborilmaydi.
3. **Mehmon (login qilmagan).** Savol 24 soat kutib turadi. Sahifa ism va telefonni
   so'raydi (`POST /api/v1/chat/handoff`), keyin shu savol bilan mehmon support chati
   ochiladi.
4. Model hech qachon «yubordim» demaydi. Nima bo'lgani javob ostida `handoff` maydoni
   orqali ko'rsatiladi.

### 2.2. Stream'dagi yangi maydon: `handoff`

`GET /api/v1/chat/stream/{turn_id}` dagi har bir freymda endi `handoff` bor.
Oxirgi freymda (`"done": true`) qiymati quyidagilardan biri bo'ladi:

| `handoff` | Kim | Frontend nima qiladi |
|---|---|---|
| `""` | — | Hech narsa, oddiy javob |
| `"sent"` | Login qilgan mijoz | Javob ostida: «✅ Savolingiz mutaxassisga yuborildi. Javob **Yordam** bo'limida keladi.» + «Yordam chatini ochish» tugmasi (`/support`) |
| `"ask_phone"` | Mehmon (login qilmagan) | Javob ostida forma: **Ism**, **Telefon**, Email (ixtiyoriy) + «Yuborish» tugmasi → 2.3 |
| `"not_sent"` | Login qilgan mijoz | Soatiga 3 tadan oshdi yoki yuborishda xato bo'ldi: «Yordam bo'limiga yozing» tugmasi (`/support`) |

Suhbat qayta ochilganda (`GET /api/v1/chat/threads/{id}`) `messages[].handoff`
xuddi shu qiymatni qaytaradi, shuning uchun yozuv sahifa yangilanganda ham qoladi.

### 2.3. Mehmon formasi: `POST /api/v1/chat/handoff`

Token kerak emas.

```json
{
  "turn_id": "<savol berilganda qaytgan turn_id>",
  "name": "Ali Valiyev",
  "phone": "+998 90 123 45 67",
  "email": ""
}
```

Maydon cheklovlari: `turn_id` ≤ 64, `name` ≤ 200, `phone` ≤ 40, `email` ≤ 254 belgi.
Email bu yerda ixtiyoriy. Yozilgan bo'lsa, tekshiriladi.

**201**: mehmon support chati ochildi. Birinchi xabarda savol va AI javobi bor:

```json
{ "token": "…", "chat": { "name": "…", "phone": "+998901234567", "messages": [ … ] } }
```

`token`ni saqlang. Keyin bu oddiy mehmon chati bo'ladi, kirish sahifasidagi «Yordam»
bilan bir xil:
- `GET /api/v1/support/guest`
- `POST /api/v1/support/guest/messages`

Ikkalasiga ham header `X-Guest-Token: <token>`.

**Xatolar:**
- `422`: `problems` ichida maydon bo'yicha xato (`name`, `phone`, `email`). Formada
  maydon ostida ko'rsating. Shundan keyin formani qayta yuborish mumkin.
- `404`: «Savol topilmadi yoki allaqachon yuborilgan.» 24 soat o'tgandan keyin ham shu
  javob keladi.
- `409`: «Savol hozir yuborilmoqda.» Birinchi so'rov hali tugamagan (ikki marta bosish
  yoki qayta urinish). Bitta savolga bitta chat ochiladi, birinchi so'rovning javobini
  kuting.
- `429`: bir manzildan juda ko'p chat ochildi.

### 2.4. Postman

1. `POST /api/v1/chat/ask` — `{"question": "Kartamdan ikki marta pul yechildi"}`
2. `GET /api/v1/chat/stream/{turn_id}` — oxirgi freymda `"handoff": "sent"`
3. `GET /api/v1/support` — savol mijozning support chatida turibdi.

Mehmon uchun:
1. `POST /api/v1/chat/ask` ni tokensiz, `{"question": "...", "guest_id": "g1"}` bilan
   yuboring.
2. Stream'da `"ask_phone"` keladi.
3. Keyin `POST /api/v1/chat/handoff`.

## 3. Reklama akkauntiga ruxsat yo'q (`account_access`)

Migratsiya **0039**: `ad_accounts.reach_lost_at`.

### 3.1. Muammo nima edi

Mijoz Meta'ni **boshqa Facebook profil** bilan qayta ulasa, eski profil orqali kelgan
reklama akkaunti kabinetda «faol, tanlangan» bo'lib qolardi. Yangi profilning esa bu

> loaded due to missing permissions… | code 100/33

Haqiqiy holat: 2026-11-09, «Baraka» kabineti. Xuddi shu xato Business Manager'da
profildan akkaunt roli olib qo'yilganda ham chiqadi.

### 3.2. Backend endi nima qiladi

### 5.5. Frontendda nima qilish kerak

**1. API turlarini yangilash.** `docs/api/openapi.json` va
`packages/api/src/gen/openapi.ts`ni backenddan qayta yarating. Hozirgi nusxa backenddan
ancha orqada, shuning uchun maydonlarni qo'lda qo'shish ham mumkin:
- `AdRowOut`ga `delivery`, `is_stale`, `synced_at`;

**2. `statusOf`: regex o'rniga `delivery`.**
`packages/api/src/live/bridges/officeClients.ts`:

```ts
const statusOf = (a: AdRow): DeliveryStatus => {
  if (a.is_running) return /learn|o.?rgan/i.test(a.delivery_label) ? "learning" : "active";
  switch (a.delivery) {
    case "paused": case "pending": case "rejected": case "finished":
    case "billing": case "unknown": case "stale": case "no_ads": case "not_read":
      return a.delivery;
    default:
      return STATUS.find(([, re]) => re.test(a.delivery_label))?.[0] ?? "unknown";
  }
};
```

Default `"paused"` emas, `"unknown"` bo'lsin: noma'lum holatni «To'xtatilgan» deyish

**3. `DeliveryStatus` va `StatusBadge`.**

## 6. Rad etilgan ishga tushirish rollback'dan keyin ham rad etilgan bo'lib qoladi

**Xato.** Meta reklama yaratishni rad etsa, yaratilgan qismlar orqaga qaytariladi
(rollback). Shundan keyin taklif yana «Deyarli tayyor / O'zgarish yo'q» bo'lib
ko'rinardi va rad etish yo'qolardi. Mijoz nima bo'lganini ko'rmasdi.

**Endi:**
- Yaratish qadamida xato bo'lib rollback qilingan ishga tushirish **muvaffaqiyatsiz
  yaratish** (`failed`) deb ko'rsatiladi. «Qayta urinish» qaytadan yaratadi.
- Meta'ning tanilmagan `refused` rad etishi endi «o'zgartirmasdan yuborsa yana rad
  etiladi» deb hisoblanmaydi. Bunday rad etishning sababi ko'pincha reklamada emas,
  akkauntda (sertifikat, tekshiruv) bo'ladi, shuning uchun qayta urinish mumkin.
- Yaratish paytidagi so'rovda (taklif hali yo'q) reklamalar soni 0 emas, ishga
  tushirishning o'z reklamalari soni bilan keladi (`ads`).

Front o'zgarishi shart emas: holat va son mavjud maydonlarda to'g'ri keladi.
